## Conflict Search Scaling

After the Customer 0 big-data seed, live conflict preview became slow when the app had to scan a much larger corpus.

The first cheap scaling path was implemented with Azure SQL full-text search:

- Added a denormalized `ConflictSearchDocuments` table.
- Added Azure SQL full-text catalog/index setup through EF migration.
- Conflict searching now uses SQL Server `CONTAINSTABLE` as the candidate finder when full-text is available.
- CMIForge still applies its own scorer after candidate lookup; SQL rank is not the final match score.
- If SQL full-text is unavailable or the candidate path cannot run, the service falls back to the original full-scan behavior.
- Live conflict preview uses the faster candidate path and avoids prior-history scanning so typing stays responsive.

Important behavior note:

- Returned result scores still come from the existing CMIForge scoring code.
- The returned set may not be mathematically identical to the old full scan for very odd fuzzy-only cases because full-text narrows candidates first.
- For normal company, matter, client, party, and alias terms, the tradeoff is much better responsiveness with the same scoring model on returned hits.

## Customer 0 Full-Text Warmup

The EF migration landed on Customer 0, but the document table initially had zero rows. Instead of relying on the first browser conflict search to rebuild a large document corpus, a repeatable operator script was added:

```powershell
.\tools\rebuild-conflict-search-documents.ps1 -AllowTemporarySqlPublicAccess
```

The script:

- Uses the same Azure CLI token/temporary firewall pattern as the big-volume seed script.
- Ensures the full-text catalog and index exist.
- Rebuilds `ConflictSearchDocuments` with set-based SQL.
- Starts full-text population.
- Prints source-type counts and a sample full-text hit check.
- Supports `-SkipHistory` when only live entities should be indexed.

Customer 0 warmup evidence:

- `40,437` total conflict search documents.
- `10,012` client documents.
- `20,010` matter documents.
- `10,018` party documents.
- Alias and prior-history document rows were also present.
- Direct `CONTAINSTABLE` queries returned generated Customer 0 hits such as Alder records.
- Azure SQL public network access was restored to `Disabled` after the maintenance run.

## Azure AI Search Discussion

Gabe asked whether Azure AI Search could be shared across databases/tenants.

Working decision:

- One Azure AI Search service could be shared across demo and Customer 0 for early testing if each tenant/environment gets its own index.
- The app should resolve the index name from trusted tenant/environment configuration, never from user input.
- Separate indexes, data sources, and indexers keep the blast radius low for early use.
- For the immediate conflict-search scaling need, Azure SQL full-text search is cheaper, simpler, and good enough.
- Azure AI Search becomes more attractive later for semantic search, vector search, richer ranking, chunked documents, and cross-field intelligence.
- Later in the same day, a Basic proof-of-tech Search service, `gw-ai-srch-basic`, was created with separate demo and Customer 0 indexes. Initial indexing completed with 53 demo documents and 40,437 Customer 0 documents.

## Azure SQL Private Endpoint Operator Access

Private endpoints are now enabled for Azure SQL and storage, and Azure SQL public network access is disabled by default.

That means a local SQL client cannot connect to `gwmatterforge.database.windows.net` through the private endpoint unless the machine is on a network path that can resolve and reach the private endpoint, such as:

- a VM inside the `cmiforge-vnet`,
- Azure Bastion into a jumpbox VM,
- Point-to-Site VPN into the VNet,
- ExpressRoute or site-to-site VPN in a future enterprise setup,
- Azure Cloud Shell only if it is intentionally integrated with the right network path,
- or a controlled temporary public access maintenance window.

SSMS is optional. The tool can be SSMS, Azure Data Studio, `sqlcmd`, `Invoke-Sqlcmd`, or a scripted Microsoft.Data.SqlClient connection. The important thing is network placement and Entra/SQL permissions, not the UI client.

For current local maintenance, the repo scripts use `-AllowTemporarySqlPublicAccess` to briefly enable SQL public access for Gabe's current public IP, perform a narrow maintenance action, remove the firewall rule, and restore public access to disabled. This is acceptable for controlled operator work, but not the default app or migration path.

Normal EF migrations should continue to run through the dedicated VNet-integrated migrator WebJob.

## Entity Directory Search Index

Gabe asked whether CMIForge should add separate Azure AI Search indexes for every entity table.

Working decision:

- Do not create one index per entity table yet.
- Use one tenant entity-directory index with `sourceType` values instead.
- Include clients, matters, parties, client aliases, party aliases, and contacts.
- Skip users until there is a clear user-search use case, because user profile and identity data should be treated more carefully.
- Keep tenant data separated by index, not by user-supplied filters.

Implemented proof-of-tech setup:

- Added SQL view `dbo.EntitySearchDocuments`.
- The view produces Search-safe document keys and exposes source IDs, parent IDs, display text, secondary text, status, archive state, entity number, searchable text, and update time.
- Created Azure AI Search indexes, data sources, and indexers:
  - `cmiforge-demo-entity-directory`
  - `cmiforge-demo-entity-directory-sql`
  - `cmiforge-demo-entity-directory-indexer`
  - `cmiforge-customer0-entity-directory`
  - `cmiforge-customer0-entity-directory-sql`
  - `cmiforge-customer0-entity-directory-indexer`
- Granted managed identity `gw-index` read access to the view.
- Initial indexing completed with `57` demo documents and `40,081` Customer 0 documents.
- Search-only checks returned Customer 0 hits for `manufacturing`, `walker`, and `alder`.
- Azure SQL public network access was restored to `Disabled` after setup and indexing.

Important note:

- The entity-directory index is prepared infrastructure. The current app screens do not yet use it as a global/entity search provider.
